# S3：HLC（混合逻辑时钟）在时钟回拨 5 秒下的排序与合并

> 状态：**已实测**（问题 / 方法 / 判定标准在实测前预登记，实测后未修改判定标准）
> 对应架构：§4.1（事件、HLC、segment 合并）、§4.3（租约）、§13（不读 obelisk 源码）。
> 日期：2026-11-18

## 1. 问题

1. 物理时钟回拨 5 秒时，HLC 是否仍能给出**因果一致**的全序？
2. 多个 actor 各自产生事件、事后合并时，HLC 时间戳是否满足：
   唯一、稳定（同一集合任意合并顺序得到同一全序）、因果优先（happens-before 必排在前面）？
3. 同一父节点（同一因果前驱）的并发事件，合并后顺序是否确定、可复现？
4. HLC 的已知局限是什么？架构给出的退路"单 actor 串行日志"何时必须启用？

## 2. 方法（实测前预登记）

- **实现**：`scripts/spikes/s3-hlc.mjs` 实现**调查原型**（非业务代码），
  采用 Kulkarni et al. 2014 的 HLC 算法：
  - 状态 `{ physical, logical }`；`send/local`：`p = max(prev.physical, now)`，
    `l = p === prev.physical ? prev.logical + 1 : 0`；
  - `receive(m)`：`p = max(prev.physical, m.physical, now)`；
    `l = p === prev.physical === m.physical ? max(prev.logical, m.logical) + 1`
    （按标准规则实现，逐分支记录）；
  - 排序键 `(physical, logical, actorId)`，actorId 仅用于**打破完全相同的物理+逻辑**
    （标准 HLC 在并发下可能相等），全程记录是否有需要 tie-break 的情况。
- **虚拟时钟**：注入 `now()`，不读真实系统时间；可脚本化前进/回拨/冻结，
  保证测试可复现。
- **场景**（全部用虚拟时钟，固定 actor 与种子）：
  - A. 单 actor 单调时钟 200 事件；
  - B. 单 actor 在事件 #200 后**回拨 5000 ms**，再继续 100 事件（共 300，与 P2 一致）；
    之后把时钟推进 6000 ms 再发 1 个事件，观察物理分量恢复。
  - C. 3 actor 并发（各 100 事件），事件间通过显式 send/receive 建立因果链，然后合并；
  - D. 同一父节点派生 3 个并发子事件（同一因果前驱），重复 50 轮，
    每轮以 6 种不同合并顺序排序，检查最终全序是否一致；
  - E. 时钟回拨 + 跨 actor 收消息（回拨后收到"未来"消息），检查状态推进；
  - F. 唯一性：合并后所有 `(physical, logical, actorId)` 是否两两不同；
  - G. 因果优先：对每条显式建立的 happens-before 边，断言排序严格小于。
- **稳定全序**：对同一事件集合，用 ≥6 种输入/合并顺序排序，比较排序结果数组是否完全相同。
- **判定输出**：每场景输出断言结果、计数器、最小反例（若有）。

## 3. 判定标准（实测前预登记，事后不改）

| # | 判据 | 通过条件 |
|---|---|---|
| P1 | 回拨不倒退 | 场景 B 中回拨后产生的事件，其 HLC 严格大于回拨前最后一个事件的 HLC |
| P2 | 回拨不丢失 | 场景 B 的 300 个事件全部存在且唯一 |
| P3 | 多 actor 合并且因果保序 | 场景 C/G 的所有显式 happens-before 边在最终全序中方向正确（0 违例） |
| P4 | 同父并发顺序确定 | 场景 D 的 50 轮 × 6 种合并顺序，排序结果完全一致（0 分歧） |
| P5 | 唯一性 | 场景 F 中时间戳两两不同（若出现相同键，必须由 actorId tie-break 且计数报告） |
| P6 | 稳定全序 | 同一集合任意输入顺序的排序结果逐元素相同 |

- **失败备选**（架构既定）：单 actor 串行日志。若 P4 或 P6 不通过，报告最小反例并建议退路。
- **注意**：P4 的"同父并发顺序确定"依赖 `(physical, logical, actorId)` 三级键；
  若 HLC 只用 `(physical, logical)`，并发事件会相等而不构成全序。本 Spike 必须
  明确报告这一点，不能把 tie-break 当作 HLC 本身的能力。

## 4. 实现与场景说明（实测）

`scripts/spikes/s3-hlc.mjs`（调查原型，455 行，无持久化/无 I/O/无业务代码）：

- `Hlc` 类实现标准 local/receive 规则：
  - local：`p = max(prev.p, wall)`；`l = p===prev.p ? prev.l+1 : 0`
  - receive：`p = max(prev.p, remote.p, wall)`；按三个分支取 `l`
    （双方 p 相同 → `max(l, lr)+1`；仅本地胜出 → `l+1`；仅远端胜出 → `lr+1`；否则 0）。
- 排序键 `(physical, logical, actorId)`；另实现仅 `(physical, logical)` 的比较器
  用于证明 HLC 本身不是全序。
- 时钟为 `VirtualClock`（固定起点 `Date.UTC(2026,0,1)`，步长 5 ms，可回拨），
  全程不读系统时间，可复现。
- 断言引擎：直接因果边 + **传递闭包**（每个事件可达的全部祖先）双重校验。

## 6. 结论

| 判据 | 结果 |
|---|---|
| P1 回拨不倒退 / P2 不丢失 | **通过** |
| P3 多 actor 合并因果保序 | **通过**（直接边 + 传递闭包 0 违例） |
| P4 同父并发顺序确定 | **通过**（依赖 actorId tie-break） |
| P5 唯一性 | **通过**（按三元组；`(p,l)` 级别重复 200 对，由 tie-break 消解并已计数） |
| P6 稳定全序 | **通过**（带 tie-break；**不带 tie-break 不成立**，实测 4 种顺序 4 个哈希） |

**判定：HLC（含 actorId tie-break）满足 S3 的全部判定标准，回拨 5 秒不产生乱序或丢事件，
不需要退回"单 actor 串行日志"。**

对架构 §4.1 的具体含义：
1. 全局顺序靠 `(hlc.physical, hlc.logical, actor)` 排序可行且合并顺序无关；
2. **必须把 actor（segment/actor id）纳入排序键**，HLC 二元组不是全序——这应写进
   ledger 的事件 schema（事件唯一键 = HLC + actor，而不是"时间戳"）；
3. 回拨期间物理分量会被钉住，事件时间戳不再逼近墙钟，恢复后一次性跳变；
   任何"按墙钟展示时间"的功能要接受这种滞后；
4. 需要为远端偏移加护栏（见 §7 第 3 条），否则一个时钟错误的 segment 会拖累全局物理分量。

## 7. 算法局限（实测确认 + 分析）

1. **物理分量钉住**（实测）：回拨后 100 个事件物理全钉在回拨前值，靠逻辑分量单调；
   回拨越长，与墙钟偏差越大，恢复后一次性跳变 +1505 ms（本例）。
2. **HLC 不是全序**（实测）：并发事件可得完全相同的 `(p,l)`（本测 200 对）；
   全序靠 `actorId` tie-break 这一**约定**，顺序本身无因果含义——actor 字典序不应被解读为
   "哪个先发生"。
3. **无远端偏移上限**（实测 case2）：远端物理 +5 s 直接把本地拖前 5 s；
   恶意或时钟坏掉的 actor 可污染全图。生产实现需上限（如拒绝 > 本地墙钟 + 阈值的远端，
   或记录为异常）——本原型未实现，需在 P1 ledger 设计时决定。
4. **HLC 排序正确 ≠ 日志完整**：不检测 segment 被整段删除（§4.1 已声明，
   由 observed 头哈希补救，S6 范围）。
5. **不保证新鲜度语义**：回拨期间 `physical` 停滞，"最近 N 秒内的事件"这类墙钟查询不可靠。
6. 未测：真实系统时钟（`Date.now()`）抖动、NTP 跳变、休眠/挂起唤醒、跨进程持久化与恢复、
   ULID 与 HLC 的耦合、租约（§4.3）过期回收、恶意构造的远端时间戳洪水。
7. 本实现为原型：单线程、内存态、无崩溃恢复，不得直接作为生产代码。
