# S7：模块解析三路线对比 Spike

> 状态：**通过**
> 日期：2026-11-18
> 范围：仅 `scripts/spikes/s7-module-resolution.mjs`、`scripts/fixtures/generated/s7/` 合成 fixtures 及其产出证据；未改根配置，未执行未知代码，未读 obelisk 源码。
> 证据：`docs/evidence/s7-module-resolution.json`

## 1. 问题

架构 §11 要求 S7 拍板模块解析路线：

1. 路线①：自写轻量解析，覆盖相对路径、tsconfig `paths`、package `exports`、workspaces（调查原型）。
2. 路线②：使用项目自带 TypeScript 依赖的 `ts.resolveModuleName`，实测依赖体积、启动、内存与解析成本。
3. 路线③：动态加载宿主项目自己的 TypeScript。用户 G10 已明确禁止；本 Spike **不实现、不加载**，只说明拒绝理由与未知降级策略。

需要用合成 fixtures 在含别名、`exports`、monorepo workspaces 的小规模场景下比较解析成功率与成本，并明确“很小规模、结果不外推”。

## 2. 方法

1. 由脚本自己在 `scripts/fixtures/generated/s7/` 生成确定性 fixture：根 workspaces、`packages/app`、`packages/lib`、应用 tsconfig `paths` 别名、库 package `exports`（含子路径），并模拟 workspace 安装链接；只写文件与解析，不执行 fixture 代码。
2. 准备 7 个 import 用例：相对路径（含 `.js`→`.ts`）、`paths` 别名、workspace 包根、workspace `exports` 子路径、跨包相对路径、缺失 workspace 包、未安装外部包。
3. 路线①：只用 Node 内置能力实现原型解析器，记录每个用例的 resolved/unknown、方法与路径，统计成功/未知数量。
4. 路线②：用 `scripts/node_modules/typescript`（项目自带依赖，版本与体积实测）的 `ts.resolveModuleName`，读取同一 tsconfig 后解析同一组用例；记录启动导入耗时、RSS 增量、单次/多次解析耗时。
5. 路线③：不执行任何 `import('typescript')` 宿主加载；记录“拒绝”状态、G10 依据、范围外应降级为 unknown 的规则。
6. 记录小规模成本（fixture 文件数、解析次数、耗时），明确不据此外推到大型真实仓库。

## 3. 通过判据

- 路线①与路线②都对同一组合成用例给出可核对结果，且失败项为显式 `unknown`，不猜路径。
- 路线②确实使用项目自带 TypeScript 依赖，版本、安装体积、启动与解析成本有实测原始数据。
- 路线③明确未实现，写明 G10 拒绝理由与未知降级；不存在宿主 TS 动态加载代码。
- 合成 fixtures 只由本 Spike 写入允许目录，未执行其中任何未知代码。
- 成本数据标注小规模、不外推；以上全部为真才写“通过”。

### 4.4 Fixture 与“不执行未知代码”

- Fixture 位于 `scripts/fixtures/generated/s7/`，由脚本清空后重新写入：10 个文件、1398 字节；根 `workspaces: ["packages/*"]`、`packages/app` 的 `paths` 别名、`packages/lib` 的 `exports` 根与 `./feature` 子路径、以及模拟 workspace 安装的 `node_modules/@fixture/lib` junction（`installMethod: "junction"`）。
- 脚本只读取 `package.json`、`tsconfig.json` 与 TS 源码文本，并调用解析 API；没有 `import`/`require` 任何 fixture 文件，证据中 `fixture.executed = false`。
- 路线②执行的 TypeScript 代码来自本项目 `scripts/package.json` 声明的 `typescript` devDependency：`F:\Agent Nihil Obstat\scripts\node_modules\typescript\lib\typescript.js`，package 根目录为 `F:\Agent Nihil Obstat\scripts\node_modules\typescript`，版本 `5.9.3`；不是宿主项目代码，这与路线③的禁止对象不同。根 `package.json` 同样声明了 `typescript@^5.9.3`，本 Spike 使用 `scripts/` 已安装的副本以避免依赖根 `node_modules` 是否存在。

## 5. 结论

**S7 通过。**

- 路线①在本组合成用例上完成相对路径、`.js`→`.ts`、tsconfig `paths`、workspace 发现、package `exports`（根与子路径）解析；5 个应解析项全部命中，2 个不可解析项显式标 `unknown`，没有猜测。
- 路线②用项目自带 TypeScript `5.9.3` 的 `ts.resolveModuleName` 得到相同状态与真实路径；代价是约 `22.5 MiB` 安装体积、约 `116 ms` 导入启动、约 `18.7 MiB` RSS 增量（单次小规模实测，不外推）。
- 路线③按用户 G10 **拒绝且未实现**：不存在动态加载宿主项目 TypeScript 的代码路径；宿主无 TS、版本超出声明范围、加载失败或未显式开启时，降级为 `unknown/heuristic`，不执行宿主代码。
- 成本结论只适用于本 Spike 的 2 个 workspace 包、7 个 import 用例，不能据此判断大型 monorepo 的绝对性能或解析覆盖率。
- 建议：默认采用路线①（零第三方运行时依赖，覆盖已测常见情形），无法解析时标 `unknown`；路线②可作为明确接受体积/启动成本的后续可选后端；路线③保持禁止。该建议是 Spike 层面的工程判断，生产实现仍需用真实项目样本校准。
