# S2：web-tree-sitter 在 Windows + Node 24 上解析 TS/JS 的稳定性与内存

> 状态：**已实测**（问题 / 方法 / 判定标准在实测前预登记，实测后未修改判定标准）
> 对应架构：§5（Structure 层）、§5.6（存储与新鲜度）、执行计划 S2。
> 日期：2026-11-18

## 1. 问题

1. 在目标环境（Windows x64、Node 24.14.0、`scripts/package.json` 指定的
   `web-tree-sitter@0.25.10` + `tree-sitter-wasms@^0.1.13`）下，
   连续解析 ≥5000 个 TS/JS 文件是否会崩溃、抛异常或出现内存失控？
2. 吞吐是多少（文件/秒、字节/秒、p50/p95 单文件耗时）？
3. 内存随解析数量如何变化？RSS / heapUsed / external / arrayBuffers 是否持续增长？
4. 解析树与查询/遍历是否必须显式 `delete()`？不删除时增长形态如何？

## 2. 方法（实测前预登记）

- **环境**：只用当前机器 Node 24.14.0；**不覆盖 Node 22**，结论不外推。
  记录 `process.versions`（node/v8/icu/unicode）与平台信息。
- **依赖**：只使用 `scripts/` 下已安装的 `web-tree-sitter` 与 `tree-sitter-wasms`，
  wasm 路径取 `scripts/node_modules/tree-sitter-wasms/out/`，不联网、不新增依赖。
- **输入**：脚本自动生成 5200 个 TS/JS 文件到 `scripts/fixtures/generated/s2/`
  （自造输入，不含真实项目数据）。文件规模分档：
  - 小型（~1 KB）×2000：import + 接口 + 函数
  - 中型（~5 KB）×2000：类、泛型、枚举、命名空间、重导出
  - 大型（~40 KB）×1200：多类 + 大量调用 + 长函数体
  文件扩展名混合 `.ts` / `.tsx` / `.js` / `.jsx` / `.mjs` / `.cjs`，覆盖
  `typescript` / `tsx` / `javascript` 三种 wasm 语法。
- **解析方式**：每种语法一个 `Parser` 实例，`Parser.parse(source)` 得到 `Tree`；
  对每棵树做一次 `rootNode` 遍历（`walk()`，统计节点数），随后 `tree.delete()`。
  另设第二段对照：**不调用 `delete()`** 解析 500 个文件，观察 GC 后内存是否回落。
- **采样**：每 250 个文件记录一次 `process.memoryUsage()`，并 `global.gc()`（`--expose-gc`）
  后记录一次，用于区分"活跃对象"与"可回收垃圾"。
- **异常**：捕获每个文件的 parse 异常与遍历异常，记录文件、错误名、消息、栈首行；
  统计异常总数与类型分布。
- **重复**：主实验串行执行一遍，记录墙钟时间；不并发（架构中 Structure 是单写者，
  解析并发不在本 Spike 范围）。

## 3. 判定标准（实测前预登记，事后不改）

| # | 判据 | 通过条件 |
|---|---|---|
| P1 | 稳定性 | 5200 个文件全部完成，进程不崩溃、不 OOM；未捕获异常 = 0 |
| P2 | 解析正确性冒烟 | ≥99% 文件 `rootNode.hasError === false`，且每类扩展名至少 1 个样本节点数 > 10 |
| P3 | 内存有界 | GC 后 heapUsed 的第 2 段到第 5 段（即 25%–100% 进度）增长 ≤ 32 MB，且最后一段 GC 后 heapUsed 不超过第 2 段的 2 倍；RSS 峰值 < 1.5 GB |
| P4 | 吞吐 | 无预设绝对阈值（架构未给）。记录实测值，仅要求 p95 单文件耗时 < 500 ms（人为设定，仅用于识别异常离群，不是性能承诺） |
| P5 | 泄漏形态 | 不 `delete()` 的对照组若 GC 后 heap 持续单调增长，则确认必须显式释放；若可回收，则记录为"依赖 GC 即可" |

- **失败备选**（架构既定）：worker 回收——每 N 次解析重启 worker。S2 只判定是否需要该备选，
  不在本 Spike 实现 worker 池。

## 6. 结论

| 判据 | 结果 | 依据 |
|---|---|---|
| P1 稳定性 | **通过** | 5220/5220 完成，解析异常 0，进程未崩溃/OOM |
| P2 冒烟正确性 | **通过** | `hasError` 0/5220；三种语法最大节点数均 > 2.3 万 |
| P3 内存有界 | **通过** | GC 后 heap 25%→100% 增长 0.15 MB；末段 6.22 MB < 2×6.07 MB；RSS 峰值 206.88 MB < 1.5 GB，且 500 文件后平台化 |
| P4 吞吐 | **通过** | p95 12.97 ms < 500 ms；实测 p50 0.155 ms、200.85 文件/s、1.84 MB/s |
| P5 泄漏形态 | **观察项** | 显式 `delete()` 后 heap 小幅下降；GC 也能回收 JS 包装对象，但 external/wasm 统计无变化，证据不足以支持"可省略 delete" |

**判定：S2 在当前环境（Node 24.14 + Windows）通过，无需启用 worker 回收备选。**
但本结论只覆盖本次 5220 个合成文件、单进程串行、约 26 秒的短时运行；
长驻进程数小时后的 wasm 内存行为、Node 22、并发解析仍未验证（见 §7）。
实现建议（非本 Spike 结论）：每棵树 `delete()`，Parser 复用，按扩展名缓存 `Language`；
单文件 40 KB 的 p95 已约 13 ms，真实仓库若含数 MB 的生成文件必须在读取前按大小跳过
（codegraph 的 1 MB 上限可作参考，但需自行实测）。

## 7. 限制

- **仅 Node 24.14.0 + Windows 10 x64；不代表 Node 22.18（项目 `engines` 下限）、Linux、macOS。**
- 输入为自造合成文件，语法分布与真实仓库不同（无巨型 barrel、装饰器元编程、复杂 JSX、
  数 MB 生成文件）；40 KB 上限是人为设定。
- 未测 worker 并发、未测 `Tree.edit` 增量解析、未测 `Query` API、未测查询缓存。
- `external`/`arrayBuffers` 对 wasm 线性内存的计量不精确；Phase B 的 500 棵小树未产生可测增长，
  不能据此推断大树或长期运行不泄漏。
- 每次采样强制 GC 会改变运行时序；吞吐是"带 GC 干扰"的下界，非纯解析极限。
- 两次运行 RSS/吞吐有 1.5×/1.2× 波动，单次数字不应作为容量规划依据。
- 未做崩溃注入（OOM、句柄耗尽、wasm 实例化失败）与恢复测试。
