# S6：三分支独立 Segment 合并 Spike

> 状态：**通过**
> 日期：2026-11-18
> 范围：仅 `scripts/spikes/s6-segment-merge.mjs` 及其产出证据；未改根配置，未读 obelisk 源码。
> 证据：`docs/evidence/s6-segment-merge.json`（含完整 git 命令输出、每个 segment 的全部事件与 observed）

## 1. 问题

架构 §4.1 规定 ledger segment 按会话/进程切分，每个文件只由自己的写者追加，文件内维护单链 `prev_hash`，**从不跨文件**；git 分支合并等于文件并集，哈希链不应断裂；每个 segment 头事件记录启动时观察到的其他 segment 头哈希（`observed`）。

需要回答：

1. 三个本地 git 分支各自新建独立 segment 后合并，是否无冲突？
2. 合并后重放事件数是否等于各 segment 事件数之和？
3. 每个 segment 自己的单链哈希是否完整、可独立校验？
4. 每个 segment 头事件的 `observed` 是否可解析，且引用的基线段头哈希可解析？
5. 是否会错误地强加“跨 segment 全链”约束？

## 2. 方法

1. 在系统临时目录创建全新 git 仓库（不碰项目仓库），设置本地 user/email 与 `core.autocrlf=false`。
2. 在主分支先提交两个 seed segment（不同 actor/session），作为三支共同的基线。
3. 从同一基线创建 `branch-a/branch-b/branch-c`，每支只新增一个自己的 segment 文件；该 segment 头事件记录基线两个 segment 的头哈希到 `observed`。
4. 依次 `git merge --no-ff` 回主分支，记录原始 git 输出、合并后文件清单与 `git status`。
5. 对合并后的每个 segment 独立重放：从 `prev_hash = GENESIS` 起校验段内单链，统计事件数。
6. 解析每个头事件的 `observed`，逐个验证引用的 segment 文件存在且头哈希匹配。
7. 明确不做跨文件 `prev_hash` 衔接；额外记录“把所有 segment 拼接后检查全链会失败”这一预期事实，不把它当失败。

## 3. 通过判据

- 三个分支均成功合并，无冲突，工作树干净。
- 合并后 segment 文件数 = 基线数 + 3。
- 重放事件总数 = 所有 segment 事件数之和。
- 每个 segment 的段内单链从 GENESIS 到末事件全部通过；不要求跨 segment 连续。
- 所有 `observed` 是合法 JSON/哈希映射，引用均可解析回头哈希。
- 以上全部为真才写“通过”。

## 5. 结论

**S6 通过。**

- 三个分支各自新增独立 segment 后顺序 `--no-ff` 合并，git 无冲突，工作树干净。
- 合并后 5 个 segment 重放事件数 `11` = 各文件事件数之和；每个 segment 的段内单链从 GENESIS 校验通过。
- `observed` 引用可解析：seed-b 能解析到 seed-a，三个分支都能解析到两个 seed 段；合并后引用仍然存在且头哈希匹配。
- 没有强加跨 segment 全链；拼接后全局链不成立被明确记录为预期行为，而不是失败。
- 本 Spike 只在本地临时仓库验证，未覆盖远端推送、真实多客户端并发写入、或分支间互相观察（分支创建时彼此不可见，按“启动时观察到谁就记录谁”的口径不记录对方）。
- 事件 ID/HLC 使用确定性标签，未复用生产 ULID/HLC 实现；这不影响本次“文件并集 + 段内单链 + observed 解析”的结论。
