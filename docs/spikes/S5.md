# S5：批次原子追加与崩溃恢复 Spike

> 状态：**通过（限本报告列出的适用项）**
> 日期：2026-11-18
> 范围：仅 `scripts/spikes/s5-atomic-append.mjs`、`scripts/spikes/s5-writer.mjs` 及其产出证据；未改根配置，未读 obelisk 源码。
> 证据：`docs/evidence/s5-atomic-append.json`（约 2.2 MB，含全部 1636 个注入点的逐条结果）

## 1. 问题

架构 §4.1 要求：一次工具调用 = 一个批次，文件锁下原子追加 `batch.begin` + 事件 + `batch.end`（含校验和）→ fsync；崩溃恢复时由**该 segment 自己的写者**截掉没有 `batch.end` 的残尾；合并进来的**别人的 segment 只读，残尾只忽略、不修改**。

需要回答：

1. 在 `batch.begin` 与 `batch.end` 之间的**每一个字节边界**强制杀死写进程，恢复后是否都不会留下半批？
2. 零字节、每个前缀、完整提交后三种状态是否分别得到正确处理？
3. 同 segment 自己的写者能否安全截断，且不破坏此前已提交批次？
4. 他人 segment 的残尾是否只被忽略，文件字节哈希完全不变？
5. 本环境（Windows / Node 24）上 fsync 与文件锁能做到什么程度？做不到的部分不能记为通过。

## 2. 方法

1. 定义可判定的 JSONL 批次格式：`batch.begin` 行、若干事件行、`batch.end` 行；`batch.end` 保存事件行拼接的 SHA-256 校验和与事件数；事件用 `prev_hash` 维护 segment 内单链。
2. 由 `s5-writer.mjs` 作为**独立 Node 进程**打开目标 segment，只写入预生成目标批次的前 N 个字节，fsync 后向 stdout 发 `READY` 并挂起；主 runner 收到 `READY` 后强制 `SIGKILL`，必要时用 `taskkill /F` 兜底。
3. 对目标批次长度 `L`，逐一注入 `N = 0, 1, …, L`（含零字节与完整提交后）。另做一组“已有已提交 seed 批次 + 目标批次”的场景，验证截断不会伤及先前批次。
4. 注入后先记录原始字节：必须精确等于 `初始字节 + 目标批次前 N 字节`；再另起一个同 segment 的**独立 writer 进程**（`s5-writer.mjs --recover`）按最后一个完整 `batch.end` 截断残尾，验证恢复后无半批、无残缺行、事件可按单链重放。
5. 在截断前将同一残尾文件复制为“他人 segment”，只读解析/重放，前后计算 SHA-256，验证字节不变、残尾被忽略。
6. 单独实测：文件 fsync；目录 fsync（Windows 可能不支持，如实记录）；Windows 上以 `wx` 独占创建实现协作锁的争用、残留锁与清理。
7. 任一批次恢复、哈希稳定性或可支持的 fsync/锁检查失败，S5 记为不通过；目录 fsync 不支持只记为“未验证能力”，不冒充通过。

## 3. 通过判据

- 所有注入点（零字节、每个字节前缀、完整提交后）恢复后均无半批；重放事件数符合预期；完整提交点事件全部保留。
- 已提交 seed 批次在所有前缀注入下均原样保留。
- 他人 segment 残尾：只读重放忽略残尾，文件 SHA-256 前后完全一致。
- 独立 writer 确实由主 runner 强制杀死，而不是自行正常退出。
- 文件 fsync、协作锁的争用与残留行为有真实输出；不支持的目录 fsync 明确标注未验证。
- 以上适用项全部为真才写“通过”。

### 4.2 注入覆盖

| 场景 | 目标批次字节 L | 注入点 | 通过 | 自身截断 | 完整提交后重放 |
|---|---:|---:|---:|---:|---:|
| `empty-file`（空文件开始） | 815 | 0..815 共 816 | 816 | 814 | 1（offset=815） |
| `after-seed`（已有 2 事件 seed 批次） | 819 | 0..819 共 820 | 820 | 818 | 1（offset=819） |
| 合计 | — | 1636 | 1636 | 1632 | 2 |

- `N=0`：两个场景各 1 次，恢复后分别保持空文件 / 仅 seed，无半批。
- `1 ≤ N < L`：每个字节前缀都被强杀；全部由自己的写者截断到上一个完整 `batch.end`。空文件场景恢复到 0 字节；seed 场景恢复到 769 字节 seed，seed 事件全部保留。
- `N=L`：批次完整写入并 fsync 后被强杀；恢复不截断，2 个事件全部可重放。
- 截断动作由独立进程 `s5-writer.mjs --recover` 执行，证据中每次注入的 `recovery` 字段记录了该进程的退出码与 `TRUNCATED truncated=... committedBytes=...` 输出；不是 runner 内存中的模拟截断。
- 1636 次注入的原始字节都精确等于“初始字节 + 目标批次前 N 字节”，没有出现写入量漂移。
- 1636 次中的每一次都创建了“他人 segment”副本并只读重放；SHA-256 前后一致次数 = 1636。
- 1636 次进程都由 runner 在 `READY` 后强制杀死；标准错误为空，无提前退出。

## 5. 结论

**S5 在本报告适用范围内通过。**

- 批次恢复的核心结论成立：`batch.begin` 与 `batch.end` 之间每个字节边界（含零字节与完整提交后）强杀并恢复后，**没有半批事件进入重放**；完整提交点的批次完整保留，已有 seed 批次不被误截断。
- “自己的写者截断、他人残尾只读忽略”成立：1632 次自身截断均正确，1636 次他人残尾读前后字节哈希全部不变。
- 独立 writer 确实是独立 Node 进程，并由 runner 强制杀死，不是进程内模拟。
- 边界与代价必须如实保留：目录 fsync 在 Windows 失败，掉电持久性未证明；锁是协作锁文件；注入前缀在强杀前已 fsync，属于“字节已持久化、批次未完成”的较强恢复场景。
- 生产实现仍需要把 `batch.end` 校验和、完整批次判定与 owner/foreign 写权限固化到 ledger 代码，并用真实文件锁策略补齐协作锁的进程崩溃/陈旧锁处理。

未发现需要改账本设计的失败项；S5 不触发“先报告用户改设计”的条件。
