## 1. 一句话复述问题与"修好了"的判据

问题：ANO 的 `history.db` 检索要在**中文 + 中英混排 + 标识符**语料上可用，架构给了 A/B/B+/C/C+ 五个候选方案，
但它们的短板全是 `[待验证]`。本 Spike 的任务不是选赢家，而是**把底层机制的真实行为钉死**，
使选型不再有"猜"的成分。

"修好了"的判据（对齐架构 Phase 0 S1 通过标准）：

1. 机制段列出的每一类行为（ICU/Segmenter 完整性、FTS5 与 trigram 可用性、短查询 MATCH 行为、
   LIKE 与 EXPLAIN QUERY PLAN、ESCAPE、大小写敏感性、码点长度、标识符拆分）都有**实际执行命令产生的原始输出**；
2. 输出可由任何人用同一命令在本机复现；
3. 结论只引用原始输出里存在的数字，不引用推断。

## 2. 范围与隐私声明（重要）

- 用户**未授权真实会话采样**（决策门 G3 的"是否同意采样用于 S1 排序盲测"未获同意；
  见 `.pm/decisions/ADR-001-G1-G3-G4-G9-G10-开工决策.md`：S1 仅机制段）。

  - **不产出任何排序结论**：没有召回@20、P@5、p50/p95 延迟、索引体积比之类的方案排名，

## 4. 方法与执行方式

### 4.1 环境

- Node 24.14.0（`process.versions` 由脚本原样写入 evidence，不手写）
- Windows 10.0.19041 x64，Git Bash
- 数据库：`node:sqlite`（`DatabaseSync`），全部使用 `:memory:`，不建库文件，不留残余
- 所有 SQL 均为**参数化**（`?` 绑定），查询词不参与 SQL 文本拼接（对齐 §6.1"检索文本不得拼进脚本"）

### 4.2 实际命令（Windows 路径带空格，必须加引号；脚本只在仓库内运行，绝不在下载目录运行）

```bash
# 1) 生成原始证据（写到仓库内 docs/evidence/）
node "<repo>/scripts/spikes/s1-search.mjs" \
  --out "<repo>/docs/evidence/s1-search.json"

# 2) 运行机制测试（标识符拆分四类边界 + 钉死的 FTS 行为）
node --test "<repo>/scripts/spikes/s1-search.test.mjs"
```

脚本自身特性：只 `import` Node 内置模块（`node:sqlite` / `node:fs` / `node:path` / `node:url` / `node:process`），
不引入第三方依赖；输出路径必须由 `--out` 传入绝对路径，否则拒绝运行（避免"在当前目录被投放的同名模块"风险面）。

### 4.3 覆盖到的具体测试面

1. **版本记录**：`process.versions.{node,icu,unicode,cldr,sqlite}`、`Intl.Segmenter` 类型、
   SQLite `select sqlite_version()`、`PRAGMA compile_options` 全量列表（含 FTS 相关项原文）。
2. **FTS5 可用性**：`CREATE VIRTUAL TABLE … USING fts5(body)`；`tokenize='trigram'`；
   `tokenize='trigram case_sensitive 1'`；`tokenize='unicode61'`；每步成功/报错原文都记录。
3. **trigram 查询矩阵**：3 行内容（二字词、三字词、中英混排各至少一行，实际 6 行含非 BMP 与特殊字符），
   对 1 / 2 / 3 码点查询（含 BMP 与非 BMP：`租`、`租约`、`租约到`、`𠮷`、`𠮷野`、`𠮷野家`、`to`、`tok`、`refresh`、`数据库`）
   分别跑 `MATCH` 与 `LIKE`，逐条记录**返回行数**与错误原文。
4. **EXPLAIN QUERY PLAN**：每条 LIKE（以及对照组 MATCH、普通表 LIKE）跑 EQP，记录 `detail` 原文；
   比较 trigram 表、`unicode61` 表、普通 B-tree 表三种形态下的计划差异。
5. **ESCAPE**：含 `_` 与 `%` 的模式各跑一次带 `ESCAPE` 的 LIKE，并跑不带 ESCAPE 的同样模式作对照。
6. **大小写敏感性**：同一 trigram 表（默认）与 `case_sensitive 1` 表，分别用 `REFRESH`/`refresh`/`RefreshToken`
   跑 MATCH 与 LIKE，记录行数差异。
7. **码点长度**：`[...s].length` 与 `s.length` 对 `𠮷`、`𠮷野家`、含 emoji/ZWJ 串的对照；
   并记录 FTS/LIKE 结果随码点数（1→2→3）的变化点。
8. **Segmenter 样本**：`refreshToken`、`refresh_token`、`XMLHttpRequest`、`parseHTMLString`、`utf8Decode`、
   `base64`、`kebab-case`、`a.b.c`、`调用refreshToken函数`、`调用 refreshToken 函数`、`𠮷野家`、以及二字术语与句子，
   逐条记录 segment 数组与 `isWordLike`；并对比 `zh`/`zh-Hans`/`zh-Hant`/`en` 四种 locale 是否改变结果。
9. **标识符拆分函数**：脚本内实现 `splitIdentifier`（确定性、不读 ICU），
   覆盖四类边界并输出子词；`node --test` 断言四类用例；函数版本号与 ICU/Unicode 版本一并写入 evidence。

### 4.4 规则细化记录（写脚本之前确定，影响 D10 的期望值；不是事后凑数）

§5 的 D10 只列了必测串，没有把"字母数字边界"细化到方向，本节把实现前就定下的规则补全，并留下测试失败痕迹（§7.11）。

| ID | 规则 | 结果 | 理由与代价 |
|---|---|---|---|
| R1 | `_`、`-`、`.`、`$` 及其余非字母数字字符一律作边界（边界本身不产出子词） | `refresh_token → refresh, token`；`kebab-case → kebab, case`；`a.b.c → a, b, c`；`$scope → scope` | 与 unicode61 的天然分隔行为一致 |
| R2 | 小写→大写边界拆 | `refreshToken → refresh, token` | 标识符子词召回的主要来源 |
| R3 | **字母↔数字两个方向都拆**，数字段独立成子词 | `utf8Decode → utf, 8, decode`；`base64 → base, 64` | 索引端与查询端同一函数：查 `base`/`utf` 能命中 `base64`/`utf8Decode`；查 `base64` 拆成 `[base,64]` 以隐式 AND 命中同一行。代价：产生 `8`、`64` 这类短数字子词，增大倒排项。是否在实现期过滤纯数字子词属性能/排序段议题，本 Spike 不改规则 |
| R4 | 连续大写缩写串在"缩写结束处"拆（大写串 + 后续小写词） | `XMLHttpRequest → xml, http, request`（不是 x/m/l）；`parseHTMLString → parse, html, string`；`HTTPServer → http, server` | 副作用：`OAuth2Token → o, auth, 2, token` 出现单字母子词；因索引端同时保留原词（`expandIdentifier` = 原词 + 子词），查 `oauth` 仍由原词 token 命中，不依赖子词 |
| R5 | 输出小写化、去重、保序；**输入域限定**为 ASCII 标识符（调用方按 `/^[A-Za-z0-9_$]+$/` 过滤） | `splitIdentifier('调用refreshToken函数') → ['refresh','token']`（CJK 部分被排除在输入域外） | 与 §6.1"对 isWordLike 且匹配该正则的片段拆分"一致 |

固化版本：`IDENTIFIER_SPLIT_VERSION = 'ano-s1-identifier-split-v1'`，实现期须与 `process.versions.icu`/`unicode`
一起写进 `meta`（§6.1 的重建锚点），任一变化即重建缓存。

## 5. 预写判定标准（在跑脚本之前固定，之后不得改）

以下标准先写好，§7 的实测与 §8 的结论只能按这些标准给出。记号：
`GT(q, col)` = 同一份合成语料在**普通表 `LIKE '%q%'`**（真值基线，不经 FTS）下的命中行数；
`M(q)` / `L(q)` = FTS 表上 MATCH / LIKE 的命中行数。

| ID | 判据 | 通过条件 | 不通过时的处置（预先约定） |
|---|---|---|---|
| D1 FTS5 可用 | `CREATE VIRTUAL TABLE …fts5` 成功 | 记录"FTS5 可用"，A–C+ 共同前提成立 | FTS5 不可用 → 方案 A/B/B+/C/C+ 全部出局，转内存倒排备选，并如实报告为 S1 机制段"部分失败" |
| D2 trigram 可用 | `tokenize='trigram'` 建表成功且 MATCH/LIKE 有返回 | 记录"trigram 可用"及版本依据（`PRAGMA compile_options` 原文） | 记录**报错原文**；架构里"不假设 trigram 可用"，据此判定 A 在本环境不可实现，不写任何 A 相关结论 |
| D3 短查询 MATCH 可靠性 | 对每个 1、2 码点查询比较 `M(q)` 与 `GT(q)` | 全部 `M(q) === GT(q)` → MATCH 短词可靠 | 存在 `M(q) < GT(q)` 且无报错 → 判定"静默漏检成立"，写入结论；`M(q)>GT(q)` → 判定 MATCH 语义宽于 LIKE，另行说明 |
| D4 3 码点及以上 | `M(q) === GT(q)` 对 ≥3 码点查询成立 | 成立 → A 在 ≥3 码点可用 | 不成立 → A 的可用性整体降级并记录 |
| D5 LIKE 是否走索引 | EQP `detail` 原文出现 fts5 虚拟索引相关字样（例如 `VIRTUAL TABLE INDEX 0:` 带 L 策略）且与普通表 `SCAN <table>` 可区分 | 记录"EQP 可区分索引使用" | 若 EQP 无法区分 → 如实写"EQP 不足以判定，需改用文档定义的条件判定"，不得凭感觉断言"走了索引" |
| D6 ESCAPE | 带 ESCAPE 的模式命中正确（`a_100%` 命中含字面量的行、不误命中通配），并记录 ESCAPE 前后 EQP 是否变化 | 行为记录完整即通过 | 结果错误或 EQP 无法解释 → 记录为"实现期需绕开 ESCAPE 路径"，并给出替代（参数化 LIKE 拆列 / 前缀列） |
| D7 大小写敏感性 | 同一查询词在大小写三种形态下的 MATCH/LIKE 行数全部有原始记录 | 记录完成即通过；不预设"应该不敏感" | 若 MATCH 区分大小写而 LIKE 不区分（或相反）→ 结论必须写明，因为查询构造器的折叠策略随之确定 |
| D8 Segmenter 完整性 | `Intl.Segmenter` 存在，且对 `租约`/`账本` 一类二字词返回**单个 ≥2 码点**的 wordLike 段（词级）而非逐字 | 词级 → 方案 B 的词粒度前提成立 | 若逐字切分（或对关键二字术语退化为逐字）→ 按架构失败备选：Segmenter 不可靠 → B/B+ 不成立，记录为"仅 C 退化版可考虑" |
| D9 标识符整词 | `refreshToken` 在 Segmenter 下是否为单一 wordLike 段 | 记录实测即可，不预设 | 若整词不拆 → 印证架构假设：B 需配子词拆分（B+）；若拆 → 写明与架构假设不符并记录原样输出 |
| D10 拆分函数四类边界 | `node --test` 对 7 个必测串全部通过，且函数版本+ICU/Unicode 版本写入 meta | 全过 → 拆分规则可固化 | 任一不过 → 不得把该规则写入实现；改规则重测，禁止放宽断言迁就实现 |
| D11 排序段 | 无真实样本 | 明确不产出任何排序结论 | ——（不适用：本 Spike 无排序数据，任何排序数字都是编造） |

补充预写规则（架构 S1 第一段第 6 项要求据 Q3 结果决定，此处先定标准）：

- **A 方案需要"长度分流"的判据**：若存在任一 `<3` 码点查询使 `M(q) < GT(q)`，则判定"A 必须分流"，
  分流阈值按 **Unicode 码点**计数（依 Q6 实测确立码点/码元差异），分流去向（原文列 LIKE 或 2-gram 列）
  由 D5/D6 的实测结果决定；两者都成立时默认选"原文列 LIKE + `degraded: unigram-scan` 标注"（架构 §6.1 已定）。
- **不预设任何方案的优劣排名**；机制段只淘汰"机制上不可行"或"必须打补丁才可行"的方案，
  淘汰理由必须能指向 evidence JSON 里的具体条目。

## 6. 原始输出位置与可复现性

`docs/evidence/s1-search.json`（schema：`ano-s1-search-evidence/v1`）为脚本直出的原始记录，字段包括

### 7.10 相邻性 / snippet / bm25 / 2-gram 列（机制补充）

- 相邻性（逐字 token 后）：`MATCH '死 锁'` → 3 行 `[1,2,3]`；`MATCH '"死 锁"'`（短语）→ 1 行 `[1]`。
- snippet：
  - trigram 表 MATCH `数据库` → `[数据库]连接池`；trigram 表 LIKE → 同样 `[数据库]连接池`；
  - B 表 MATCH `租约` → `[租约] 到期 提醒`、`修复 死 锁 后 回 滚 事务 并 更新 [租约]…`（**展示的是切分后的 token 文本**）。
- bm25 多列加权（3 行合成语料）：`weights=[4,1]` 与 `[1,4]` 两次运行的分数值相同（row2 `-1.796875e-6` < row1 `-1.763066e-6`，次序未变）。
- CJK 2-gram 列（`gram`，CJK-only）：`租约` → 2 行；`租`（1 码点）→ **0**；`token` → **0**。

## 8. 结论（只根据 §7 的实测，逐条对应 §3 的问题与 §5 的判定标准）

### 8.1 逐条回答

- **Q1（Segmenter 完整性）**：`Intl.Segmenter` 存在，`zh`/`word` 对**部分**中文词返回词级单段
  （`租约`、`账本`；混排句中的 `函数`、`事务`、`更新`），但对多个常用领域词逐字切分：
  `调用→调|用`、`死锁→死|锁`、`回滚→回|滚`、`幂等→幂|等`、`数据库→数据|库`。
  四种 locale 输出完全相同。按预写 D8（"`租约`/`账本` 一类二字词返回单个 ≥2 码点 wordLike 段"）判定**通过**；
  但"词级切分对本机 ICU 的领域词普遍成立"**不成立**，这是 §7.2 的原样记录，不外推覆盖率。
- **Q2（FTS5 / trigram）**：FTS5 可用（`ENABLE_FTS5` 在编译选项中），`trigram` 与
  `trigram case_sensitive 1` 均可建表，无报错。D1、D2 通过。
- **Q3（短查询 MATCH）**：1、2 码点查询的 MATCH 全部**静默 0 行**（8/8，且 `error === null`），
  而 LIKE 在 15/15 个查询上等于真值。D3 判定"静默漏检成立"；3 码点及以上的 MATCH 等于真值（D4 通过）。
- **Q4（LIKE 是否走索引）**：EQP 能把"fts5 接管 LIKE"与全表扫区分开：trigram 表不带 ESCAPE 的 LIKE 显示
  `VIRTUAL TABLE INDEX 0:L0`；普通表是 `SCAN t_plain`；`unicode61` 表、带 ESCAPE、`case_sensitive 1` 表都不显示 `L0`。
  但 1/2/3 码点 LIKE 的 EQP **相同**（都是 `L0`），因此 EQP **不能**证明短模式真的用到了三元组索引——
  本报告不写"短 LIKE 已走索引"。D5 判定为"部分可区分"。
- **Q5（ESCAPE / 大小写）**：ESCAPE 语义正确（`%a_b%` 命中通配诱饵 1 行；`%a\_b%` 0 行；字面 `%`、字面 `_100` 均 1 行且等于普通表真值）；
  带 ESCAPE 后 EQP 丢失 `L0`。大小写：默认 trigram 折叠（MATCH/LIKE 均 2 行）；`case_sensitive 1` 下
  **MATCH 区分大小写**（`REFRESH`→0，`refresh`→1，`Refresh`→1，`Token`→2、`token`→1），而 **LIKE 仍 ASCII 不区分**（2 行）；
  普通表上 `COLLATE BINARY` 对 LIKE **无效**（两种模式都 2 行）。D6、D7 记录完整，通过。
- **Q6（码点）**：`𠮷` 的 JS 码点/UTF-16 为 1/2，SQLite `length()`=1、UTF-8 4 字节；trigram 阈值按**码点**：
  `𠮷`(1)→0、`𠮷野`(2)→0、`𠮷野家`(3)→1=真值。长度分流必须用 `[...s].length`。
- **Q7（UAX #29 标识符）**：`refreshToken`、`refresh_token` 在 Segmenter 下都是**整词单段**；`调用refreshToken函数`
  → `调|用|refreshToken|函数`（中英紧邻处 `用|refreshToken` 断开，`refreshToken|函数` 断开）。
  因此整词索引时查 `token`/`refresh` 会漏：B 模拟实测 0 行，B+ 模拟 1 行。D9 通过（架构假设被证实）。
- **Q8（拆分函数）**：7/7 预写用例通过，规则 R1–R5 与版本 `ano-s1-identifier-split-v1` 已固化（§4.4、§7.3）。
- **Q9（unicode61 原始串）**：未经预处理的连续 CJK+拉丁串在 `unicode61` 下是**单一 token**：
  `租约`、`refreshtoken`、`REFRESH`、`𠮷野家` 的 MATCH 全是 0，只有整串
  `调用refreshToken函数更新令牌` 能命中 1 行。→ 方案 B 必须"先 Segmenter 切分、以空格连接后再入库"（§7.9）。
- **Q10（A 是否要长度分流）**：`summary.lengthRoutingNeeded = true`，依据 §7.4 的 8 个静默 0 行用例。
  分流阈值按码点：`<3` 码点走原文列 LIKE（并可标 `degraded`）或 2-gram 列（视 `租约`→2 行、`租`→0 行的实测，
  2-gram 只覆盖 2 码点，1 码点仍须 LIKE）。

### 8.3 对候选方案的机制性含义（**不是排名，不比较优劣**）

- **A（trigram）**：MATCH 只在 **≥3 码点**时与真值一致且不报错；`<3` 码点必须分流（Q10）。
  LIKE 短模式在 EQP 上仍标 `L0`，但无法据此断言高效；**带 ESCAPE 时 `L0` 消失**（§7.5、§7.6），
  因此"用 ESCAPE 保证字面量语义"与"保留 trigram LIKE 加速"在实测层面冲突，需在实现期二选一或改写查询。
  MATCH 查询词含 `%` 直接报错（§7.7），必须双引号包裹。
- **B（Segmenter + unicode61）**：原始串直接入库不可用（整串单 token，§7.9）；预处理后中文查询可命中，
  但标识符整词导致 `token`/`refresh` 漏检（0 行），且领域词逐字切分会丢相邻性（AND 3 行 vs 短语 1 行，§7.10）。
- **B+（B + 子词）**：追加子词后 `token`/`refresh` 命中 1 行（§7.9），拆分规则已固化并可测（§7.3）。
- **C（词列 + CJK 2-gram 列）**：2-gram 列覆盖 2 码点（`租约`→2 行），但不覆盖 1 码点（`租`→0）与标识符子串（`token`→0）；
  `bm25()` 多列加权 API 可用（数值见 §7.10；3 行合成数据不构成任何排序结论）。
- **C+**：由 B+ 的子词产物与 2-gram 列组合，机制上可行；索引体积与权重属排序段，本 Spike 不测。
- **共同前提**：FTS5 可用；查询长度按码点；`MATCH` 词需引号化；FTS 列（尤其 B/B+ 的切分文本）不可用于 snippet
  （§7.10 的 B 表 snippet 输出即切分后文本），展示必须取原文列。
